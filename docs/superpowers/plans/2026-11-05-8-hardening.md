# Step 8 — Hardening Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Transient failures are retried at every level. A section that still fails no longer sinks the whole fill: the user sees which fields could not be filled and retries only those with one button. Answer quality is measured against the ground truth of both annexes.

**Architecture:**
- **Retries:** a `RetryingLLM` wraps any `LLM` in `app/llm/`. Adapters tell a transient failure from a permanent one with a new `TransientLLMError`.
- **Fill engine and job:** the engine keeps the run that worked when the other one fails (its answers become `unsure`). The job catches a group's final `LLMError` and records the group's fields in `form_fill.ai_failed_field_ids`. `POST /forms/{id}/fill/retry` re-runs only those fields.
- **Front:** TanStack retries transient errors only. A banner with *Retry* sits above the field list, and Next error pages catch crashes.
- **Evaluation:** an offline fill script, shared with `record_llm.py`, feeds `scripts/evaluate.py`, which writes `docs/EVALUATION.md`.

**Tech Stack:** FastAPI, SQLAlchemy 2.1 + Alembic, OpenAI SDK, pytest · Next.js 16, TanStack Query 5, next-intl, Vitest + MSW, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-05-8-hardening-design.md`

## Global Constraints

- Only `app/llm/` imports `openai`. No "AI" word, HTTP code, exception name or trace in any user-facing text (UI and API `detail`).
- Model calls get 3 attempts in total, with delays of about 2 s then 4 s plus jitter. `Retry-After` is honoured when it is ≤ 30 s. The SDK runs with `max_retries=0` and `timeout=90`.
- Indexing gets 3 attempts on unexpected errors. `UnreadableDocumentError` is never retried.
- Front queries: up to 3 retries on network errors or status ≥ 500, never on 4xx. `PATCH` field saves and `DELETE /fill`: up to 2 retries with the same rule. `POST /fill`, `POST /fill/retry` and document upload: no retry.
- When only one of the two runs fails, the section is kept and its non-cross-checked answers are `unsure` (To check). A section fails only when every run fails.
- Retry delays are settings, set to 0 in tests and e2e. No test sleeps for real.
- All interface text goes through next-intl (`en.json`). `global-error.tsx` is the one allowed exception: it renders outside the providers and gets a targeted ESLint disable.
- Paid evaluation: 3 runs per annex, about $0.20 in total. Each run's result is reported to the user before the next one starts.
- After API changes: `make gen-api`. After model changes: an Alembic migration and `make db-schema`.

## Review Focus

1. **A section fails after some of its fields were already published.** Those fields keep their answers and are not in `failed_field_ids`. Task 3 test: `test_fields_published_before_a_group_failed_are_not_failed`.
2. **The user fills a failed field, then clicks Retry.** That field is not re-run and the banner count drops. Task 4 test: `test_retry_skips_fields_the_user_filled` and Task 7 screen test.
3. **Retry while a retry is running, or with nothing left to retry.** Both return 409 with a plain message. Task 4 tests.
4. **Reload after a failed or partial fill.** The banner and the message come back from `ai_run`, not from the stream. Task 7 screen test `shows the failed banner after a reload`.
5. **Discard during a Retry.** The retry stops silently and nothing is written into a new fill. Task 4 test `test_discard_during_a_retry_stops_it`.
